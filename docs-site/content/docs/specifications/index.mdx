MDXPad follows **Specification-Driven Development (SDD)** — every non-trivial feature begins with a written specification before any implementation starts.

## Philosophy

Writing a specification first forces clarity about what a feature should do and why, before the complexity of implementation is introduced. Specifications serve as:

- A design review artifact that can be critiqued and revised cheaply
- A contract between the author and reviewer about what "done" means
- Living documentation that explains the rationale behind implementation choices
- The source of acceptance criteria for tests

## Specification Structure

Each specification covers:

1. **Overview** — What the feature does and why it is needed
2. **Rationale** — Why this approach was chosen over alternatives
3. **Architecture** — How it fits into the existing system (process model, data flow)
4. **API / Interface** — Public APIs, IPC channels, component props
5. **Acceptance Criteria** — Testable conditions that define "done"
6. **Testing Strategy** — Unit, integration, and E2E test plans
7. **Security Considerations** — Any security implications
